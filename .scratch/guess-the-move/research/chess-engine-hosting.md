# Chess engine choice & hosting — research

Research for [issue 17](../issues/17-chess-engine-choice-hosting.md). Scope per [issue 02](../issues/02-engine-execution-architecture.md): server-side, on-demand, once per unique Guess per Round (not once per Participant), up to ~30 concurrent Participants (so at most a handful of unique moves per Round), Host-paced (not timed), cloud-hosted.

## 1. Stockfish: native binary (spawned, UCI) vs WASM in-process

**Official source:** Stockfish is distributed as a headless UCI engine with no bundled GUI/API — "Stockfish does not include a graphical user interface (GUI)... requires a UCI-compatible" front end, and integrators are pointed at the UCI protocol docs. ([official-stockfish/Stockfish README](https://github.com/official-stockfish/Stockfish), [UCI Protocol and Stockfish Commands](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html))

The official releases ship precompiled native binaries per platform/CPU-feature (avx2, bmi2, avx512, vnni, apple-silicon, etc.), built from every commit and tagged releases. ([Releases · official-stockfish/Stockfish](https://github.com/official-stockfish/Stockfish/releases))

WASM builds (`stockfish.wasm`, `stockfish.js` on npm, maintained by Nathan Rugg for Chess.com's in-browser engine) exist specifically **because browsers can't spawn native processes** — they're a sandboxing workaround, not a performance upgrade. The project's own README steers most integrators toward the smaller "lite" single-threaded build because "the full engine is so large it can be very slow to load," and flags the plain asm.js fallback as "very slow and weak." ([nmrugg/stockfish.js](https://github.com/nmrugg/stockfish.js)) In Node.js, using the WASM build additionally requires experimental flags (`--experimental-wasm-threads --experimental-wasm-bulk-memory`) to get multi-threading at all, and community wrappers like `@se-oss/stockfish` and `shahradelahi/node-stockfish` exist mainly to paper over that setup. Independent measurements put WASM at roughly 2–2.5x slower than a native build at equivalent search effort, and even Lichess's own forum discussion of its browser engine notes that WASM search reports a higher nodes/sec figure but reaches lower actual depth than a native binary in the same time, because of WASM overhead, thread caps, and evaluation-net differences. ([Hacker News discussion citing Lichess team](https://news.ycombinator.com/item?id=29572790), [Lichess forum: Stockfish testing with multi-threaded WebAssembly](https://lichess.org/forum/lichess-feedback/stockfish-testing-with-multi-threaded-webassembly))

**Conclusion:** the WASM build's entire reason to exist is "no native process spawning available" (i.e., browser sandbox). A Node.js server has no such restriction — it can spawn the native binary directly. There is no upside to running WASM in-process on a server; it's strictly slower and fussier to configure than `child_process.spawn()` talking UCI over stdin/stdout. **Use the native binary via UCI**, not a WASM build.

**Licensing:** Stockfish is GPLv3, not AGPL. ([official-stockfish/Stockfish README](https://github.com/official-stockfish/Stockfish)) GPLv3 has no network-use clause, so running it as a backend process that clients talk to over HTTP/WebSocket does not require distributing source to those clients — only distributing the *binary itself* would trigger GPL's source-availability obligations. Self-hosting it server-side for this app carries no meaningful licensing friction.

### Latency at a live-interactive time budget

Primary UCI docs confirm `go movetime <ms>` and `go depth <n>` as the two natural ways to bound a single evaluation: "Stop the search when approximately x ms have passed" / "when depth x has been reached." Recommended setup order is `Threads` (≈ CPU cores available) then `Hash` (transposition table size), with `MultiPV` left at 1 for a single best-line evaluation. ([UCI Protocol and Stockfish Commands](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html))

For throughput, Stockfish's own benchmark documentation states current NNUE builds should reach "at least 1 MNPS (million nodes/sec) per core" on modern cloud CPUs (e.g. GCP c4d with an avx512icl build). ([official-stockfish/Stockfish benchmark notes, via amdw/enginecloud SF_BENCHMARKS.md](https://github.com/amdw/enginecloud/blob/main/stockfish/benchmarks/SF_BENCHMARKS.md)) At that rate, a 1–2 second `movetime` budget on a single modern core searches on the order of 1–2 million nodes — comfortably into double-digit ply depth for a typical middlegame position, which is far more than needed to place a human Guess into a coarse accuracy band (this app's use case, not finding the objectively single best engine move). A few hundred ms to ~2s per position, single-threaded, is a realistic and generous budget at this project's scale — not a stretch for a small cloud VM.

## 2. Managed/hosted chess analysis APIs

**Lichess cloud eval (`GET /api/cloud-eval`)** is the only credible managed option and it does not fit this use case. It is a **read-only lookup against a precomputed cache** of ~320 million positions (mostly opening theory), not on-demand engine analysis: "Access Lichess's cloud evaluations database" — positions not already in the cache return `404`, and the database is fed by trusted contributors' prior submitted analyses, not fresh computation per request. ([lichess-org/api spec, `api-cloud-eval.yaml`](https://github.com/lichess-org/api/blob/master/doc/specs/tags/analysis/api-cloud-eval.yaml); confirmed via community reports of 404s on uncached/obscure positions, e.g. [Lichess forum: How does cloud analysis work?](https://lichess.org/forum/lichess-feedback/how-does-cloud-analysis-work-2)) Since this app must evaluate **any legal move a Participant might guess** (issue 02 explicitly rules out anticipating only some moves), most submitted Guesses — especially past the opening, or slightly offbeat tries — will simply miss the cache and return 404 with no fallback evaluation. That's disqualifying on its own, independent of its rate limit (3,000 requests/day/IP, confirmed both in community reports and Lichess's own source, `lila/app/controllers/Api.scala`).

No other reputable *managed, pay-for-arbitrary-position-analysis* chess API turned up in primary-source search (Chess.com's API is game/player data, not an analysis-on-demand service; third-party "chess API" wrappers found are themselves thin proxies in front of a self-run Stockfish, not a distinct hosted analysis product). **Conclusion: no managed API replaces self-hosting here** — the project's earlier decision to run its own server-side engine (issue 02) is the only viable path, which this research corroborates rather than overturns.

## 3. Concurrency/process-pool sizing at ~30 participants

Per issue 02's already-settled architecture, evaluation is deduplicated per unique submitted move per Round, not per Participant — with ~30 Participants guessing one Featured Side move per Round, the realistic fan-in is "a handful of distinct legal moves," not 30 simultaneous evaluations. Round pacing is Host-triggered (not a hard timer), so there's slack to queue rather than needing all evaluations to complete within a tight synchronous window.

Given `go movetime` bounds each evaluation to a fixed wall-clock cost (e.g. 1s) regardless of position, and Threads should be set to the cores available to *one* engine process ([UCI doc](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html)), the practical choices are:
- **One long-lived Stockfish process per small VM/container, driven by an in-process work queue** that serializes evaluation requests (one `position` + `go` + read `bestmove`/score per queued move) — for "a handful" of unique moves at ~1s each, worst case (say 6 unique moves) is ~6 seconds of queued latency before the last one resolves, well within a Host-paced Reveal flow.
- If lower worst-case latency is wanted, run a **small pool of 2–4 engine processes** (still trivial on a single small VM — each process is cheap when Threads=1 and Hash is modest, e.g. 64–128MB), so a handful of unique moves evaluate in parallel rather than strictly serially. This is the "stockfish-cluster"/worker-pool pattern documented in community references (e.g. `Yengas/stockfish-cluster-example`, `StockfishPool`-style libraries) built directly on `child_process.spawn` + UCI over stdin/stdout.

**Conclusion:** at this scale, **a single engine process with a simple queue is sufficient**; a small pool (2–4 processes) is a cheap, low-risk upgrade if you want near-parallel evaluation of the handful of unique moves per Round, but nothing resembling a fleet, autoscaling, or per-request container spin-up is warranted. This is a single small VM/container problem, not a distributed-systems problem.

## 4. Cost ballpark

Self-hosting the native Stockfish binary needs only a small, cheap compute instance — this workload is bursty (only active during a live Session) and CPU-light in aggregate (a handful of ≤2s evaluations per Round), so a pay-per-use/scale-to-zero container is the natural fit rather than a 24/7 box:

- **Fly.io** `shared-cpu-1x` machines are metered per second of active use: 256MB ≈ $0.0027/hour, 512MB ≈ $0.0041/hour, 1GB ≈ $0.0068/hour, unchanged in Fly's October 2026 pricing update. ([Fly.io Pricing](https://fly.io/pricing/), [Updated pricing, effective October 1, 2026](https://fly.io/pricing-update/)) A single-event Session running a few hours costs on the order of **a few cents to low tens of cents** for the whole event if the machine is stopped/scaled to zero between events (Fly machines and similarly-billed containers like Cloud Run/Fargate bill only while running).
- Compare to Lichess cloud eval, which is free but — per section 2 — architecturally unsuitable regardless of cost (it doesn't evaluate arbitrary on-demand positions), so there's no real "managed API price" to weigh against self-hosting; self-hosting is not just cheaper, it's the only workable option.

**Conclusion:** cost is a non-issue at this scale either way — self-hosting a native Stockfish process on a small, scale-to-zero cloud instance costs cents per event, which fits "occasional, single-event usage" far better than provisioning anything larger or paying for a managed service that can't actually do the job.

## Recommendation

**Run the official native Stockfish binary as a spawned child process, driven over stdin/stdout via the UCI protocol, on a single small cloud VM/container** (e.g. Fly.io `shared-cpu-1x`/1GB or equivalent), scaled to zero between Sessions. Bound each evaluation with `go movetime 1000` (1 second; adjust between ~500ms–2s to taste), `Threads` set to the instance's core count, modest `Hash` (64–128MB is plenty for single positions), `MultiPV 1`. Serialize evaluations through a simple in-process work queue against one engine instance; if near-parallel evaluation of a Round's handful of unique Guesses is desired, bump to a small pool of 2–4 engine processes — no more is justified at ~30 Participants. Do **not** use a WASM Stockfish build server-side (it exists only to work around browser sandboxing, and is measurably slower and more finicky than spawning the native binary directly in Node). Do **not** rely on Lichess's cloud eval API or any other managed analysis API — it's a precomputed-cache lookup, not on-demand evaluation of arbitrary positions, and will 404 on exactly the offbeat Guesses this app needs scored. At this project's scale, this is a same-day, near-zero-cost, single-VM decision, not an infrastructure project.

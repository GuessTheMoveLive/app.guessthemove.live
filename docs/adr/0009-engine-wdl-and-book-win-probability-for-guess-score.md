# Source Guess Score's win-probability from engine WDL and Book outcomes, not a centipawn-derived formula

**Status**: accepted (extends [0004](./0004-win-probability-loss-tiers-over-hand-typed.md) and [0006](./0006-rank-based-plus-3-ceiling.md); narrows which number counts as "win-probability" for Guess Score only — Feedback's Assessment Symbol bands and the Variant's displayed Evaluation are untouched)

Comparing this app's Guess Score against chessgames.com's own Guess-the-Move quiz for the same position (Capablanca-Marshall, move 5) showed the two disagreeing sharply: our 5. d3 (the move played) scores +3 only via the fixed played-move override, while the objectively stronger-by-our-own-Stockfish 5. d4 scores lower, and two other engine-sound tries (5. h3, 5. Ba4) score 0 on chessgames.com despite a similarly small eval loss here. Digging into why surfaced two separate gaps: chessgames.com blends its own engine (Toga) with Opening Explorer data for early moves rather than scoring on engine eval alone, and — independently — ADR 0004's logistic-curve conversion from centipawns to win-probability can't tell two moves apart when both evaluate to ~0.00 pawns but have very different practical winning/drawing chances, since Stockfish's own WDL model already distinguishes these and the pawns number alone doesn't (the "0.00 evaluation problem"). We decided to source Guess Score's win-probability from the engine's native WDL output (**Engine Win Probability**) instead of deriving it from centipawns, and, for moves still inside a large-enough Lichess Masters sample, to use that sample's own outcome stats (**Book Win Probability**) ahead of the engine figure — on the view that "is this move sound at the level this app's games are drawn from" is better answered by how master games with this position actually turned out than by an engine's abstract evaluation of an opening-stage position.

## Considered Options

- **Narrow the existing loss bands** (tighter cutoffs on the same centipawn-logistic formula): rejected — doesn't touch the 0.00-evaluation blind spot, and doesn't address that engine eval alone can rate an opening move highly while master practice disagrees.
- **Blend WDL and book stats into one weighted score**: rejected for now — Book Win Probability already stops applying automatically once a position leaves Book (or its Masters pool is too thin), so a straight handoff needs no weighting scheme to design or justify.
- **Also replace Feedback's Assessment Symbol / Evaluation display with the same win-probability sourcing**: rejected — Evaluation's centipawn figure has a separate consumer (Assessment Bonus, Variant display) with its own band logic (`feedback.ts`'s `evalToSymbol`) that isn't the thing this decision is fixing; scope stays on Guess Score's own tiering.

## Consequences

- The move actually played keeps its fixed +3 override (0004) regardless of which win-probability source backs it.
- A position counts as In Book only while its Lichess Masters pool has ≥50 games; below that (or once a position leaves known theory altogether), Guess Score falls back to Engine Win Probability, same as every move today.
- Book Win Probability is read from Masters' outcome stats (win/draw/loss rate), not raw move-popularity — a commonly-played-but-unsound try shouldn't outscore a rarer, sounder one.
- Both signals are authored offline, same as today's Evaluation: the Stockfish 19 depth-16 multiPV pass already run for every Featured Game already reports WDL in its UCI output, so capturing Engine Win Probability needs no new tooling, only an added field in the authoring step; Book Win Probability needs a new offline Lichess Masters lookup per opening move.
- Existing Featured Games (Capablanca-Marshall, Bernstein-Capablanca) keep scoring off the centipawn-logistic formula (0004) until someone manually re-authors their answer keys with the new fields — there is no forced migration, same spirit as 0006's consequences. The new sourcing applies to newly-authored games going forward.
- Feedback's Assessment Symbol bands, the Assessment Bonus, and the Variant's displayed Evaluation are unaffected — they keep reading the raw centipawn Evaluation exactly as before.
